# AiR free-tier classroom setup

Prepared September 14, 2026. The public website stays on GitHub Pages. The
existing Node application runs on **Render Free**, with a **TiDB Cloud Starter**
database. Google provides member sign-in. No AI API subscription is needed for
this guided workspace.

## Free-plan boundaries

- Render: choose the Free instance and a free workspace. One service shares
  750 free instance hours per month with the workspace. It sleeps after 15
  minutes without traffic and can take about a minute to wake. Treat this as
  a classroom pilot; Render does not recommend free instances for production.
- TiDB: choose **Starter**, with its **spending limit set to $0**. Do not select
  Essential or Dedicated. Starter includes a monthly free quota; reaching it
  can interrupt service until the quota resets. Keep the limit at zero.
- Do not add a payment card or enable paid overages. If a pre-existing Render
  account has billing enabled, check its bandwidth and build-minute spending
  controls before deploying; a free server does not make all overages free.
- Text, project notes, reflections, and result links are stored in TiDB.
  Media uploads require a separate object-storage service and are not included
  in this initial setup. Never save uploads on Render's temporary filesystem.

Sources: [Render Free](https://render.com/docs/free),
[TiDB Starter creation and spending limit](https://docs.pingcap.com/tidbcloud/create-tidb-cluster-serverless/).

## 1. Create the persistent database

1. Sign in at [TiDB Cloud](https://tidbcloud.com/). Create a Starter cluster named
   `air-classroom`; prefer AWS Virginia to match the server region if offered.
2. Confirm the spending limit is **$0** before creating it.
3. Complete the database-password step privately in TiDB. Keep the generated
   password in your password manager, never in GitHub or chat.
4. In TiDB's SQL editor, create the application database:

   ```sql
   CREATE DATABASE IF NOT EXISTS air;
   ```

5. In **Connect**, obtain the host, port, and username. Use database `air` in
   the MySQL connection URL. URL-encode special characters in the username
   and password. Enter the URL directly into Render's `DATABASE_URL` setting.
   The application enables certificate and hostname verification for TiDB.
   The same settings are used by migrations and the setup checker.

Reference: [TiDB Node connection guide](https://docs.pingcap.com/developer/dev-guide-sample-application-nodejs-mysql2/).

## 2. Deploy the server

The repository root (local `AiR/site`) contains `render.yaml`. It specifies a
single Free Docker service, automatic JWT-secret generation, five database
connections maximum, and a lightweight health probe. No Render database,
disk, background worker, cron job, or paid pre-deploy job is requested.

1. Push the reviewed application changes and blueprint to the deployment
   branch of `borngifted/air`.
2. In [Render](https://dashboard.render.com/), choose **New → Blueprint** and
   connect `borngifted/air`. If repository installation is requested, select
   only this repository. Select the branch containing the new code and inspect
   the plan before deployment. If a service named `air-platform` already
   exists, use a different name rather than modifying it accidentally.
3. Enter `DATABASE_URL`, Google client ID/secret when available, and the
   verified Google email that should administer AiR (`OWNER_EMAIL`). The JWT
   secret is generated by Render; do not replace it on each deployment.
4. The server runs `scripts/start.mjs`, which applies migrations before startup. A failed migration stops the
   launch. Repeated starts only apply migrations not already recorded.
5. Render assigns an HTTPS URL. The app uses `RENDER_EXTERNAL_URL` as the
   callback origin until you configure `PUBLIC_API_ORIGIN` explicitly.
6. Auto-deploy is disabled in this blueprint. Use **Manual Deploy** when the
   configuration is ready and for later reviewed releases.

Google setup needs the assigned service address, so the first launch can be
used to establish the URL before completing Google credentials. Sign-in
remains unavailable until both Google values are correct. Do not use fake
credentials to claim a successful sign-in test.

Reference: [Render Blueprints](https://render.com/docs/blueprint-spec),
[Render default environment variables](https://render.com/docs/environment-variables).

## 3. Connect Google sign-in

Use [Google Cloud Console](https://console.cloud.google.com/) to create a Web
OAuth client for AiR. Request only `openid`, `email`, and `profile`. Configure
the consent screen and add the exact callback:

```text
https://YOUR-ASSIGNED-HOST.onrender.com/api/oauth/callback
```

Put the client ID and secret directly into Render's environment settings.
Use designated test accounts while the Google app is in testing; complete
Google's publishing requirements before inviting the whole class. No Google
Cloud billing account is required just to use this OAuth sign-in flow.

## 4. Connect the existing website

First test the dashboard directly on the Render address. The server serves
the entire app and API together, so that test does not depend on third-party
cookies.

For the final GitHub Pages connection, add a subdomain of the existing domain,
such as `app.aireadiness.me`, to Render. Add **only that subdomain's** DNS record
in GoDaddy, using Render's displayed target, and wait for HTTPS verification.
Keep the existing apex and `www` GitHub Pages records intact.

Set Render's `PUBLIC_API_ORIGIN=https://app.aireadiness.me`, keep
`FRONTEND_ORIGIN=https://aireadiness.me`, and register the corresponding Google
callback `https://app.aireadiness.me/api/oauth/callback`. This keeps the public
site and backend on the same site for browser cookie handling. Using an
unrelated `onrender.com` backend from GitHub Pages can fail when third-party
cookies are blocked; do not launch that arrangement without addressing it.

Only after the backend is ready, set the root `air-config.js` to:

```js
window.AIR_CONFIG = { apiOrigin: "https://app.aireadiness.me" };
```

Build and publish the updated Pages client, preserving that file. See
[independent-hosting.md](independent-hosting.md) for the existing publish flow.

## 5. Activation checks

- `/api/health` returns `{"status":"ok"}`. This is a liveness check only,
  not proof of a working database or Google sign-in.
- Run `pnpm check:setup` with the production configuration securely supplied
  locally, or use the equivalent database checks from TiDB. Free Render has
  no interactive shell. Do not paste secrets into shell command history.
- Sign in with Google from the public site and reach onboarding/dashboard.
- Save an idea, add the result and process notes, finish, reload, and complete
  the five backward reflections.
- Check a second Google account cannot access the first account's project.
- Check an ordinary member cannot enter administrator pages.
- Before class, open the app once and allow it to wake; keep a printable
  activity available if a free service is unavailable. Do not configure an
  automated ping to evade the free-plan sleep behavior.
